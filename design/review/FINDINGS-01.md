| 1. Can a worker create authority indirectly, via any path? | **FAIL** | The activation algorithm permits an indirect grant path: it filters requests by ceiling, mode and role, but verifies a live grantor only for HUMAN-class capabilities. An ORD capability requiring an explicit human grant can therefore survive without that grant. See [design/authority-matrix.md:238](../authority-matrix.md#L238), [design/authority-matrix.md:243](../authority-matrix.md#L243), and the human-only grantor for `roadmap.writeback` at [design/authority-matrix.md:74](../authority-matrix.md#L74). F01-001. |
| 2. Does any state require a different transition graph in SUPERVISED vs AUTONOMOUS? | **PASS** | No separate graph is required. Both modes use the same states and transition rows, with mode-specific policy verdicts. `DENY`, including the autonomous project-creation restriction, is a policy gate on that shared graph. See [design/transition-matrix.md:43](../transition-matrix.md#L43), [design/transition-matrix.md:54](../transition-matrix.md#L54), [design/transition-matrix.md:84](../transition-matrix.md#L84), and [design/domain-model.md:716](../domain-model.md#L716). The shared graph nevertheless has the startup defects in F01-006. |
| 3. Can review or validation loops run unbounded? | **PASS** | No, under the specified enforcement of finite budgets and run deadlines. Validation retries have a schema maximum of 16; contract deadlines have a maximum of 604800000 ms; both VALIDATING and REVIEWING have deadline exits. Exhausted budgets suspend work, and extensions require human decisions. See [design/schema/stage_contract.schema.json:382](../schema/stage_contract.schema.json#L382), [design/schema/stage_contract.schema.json:86](../schema/stage_contract.schema.json#L86), [design/transition-matrix.md:194](../transition-matrix.md#L194), [design/transition-matrix.md:198](../transition-matrix.md#L198), and [design/transition-matrix.md:165](../transition-matrix.md#L165). There is no separate review-round maximum in [design/domain-model.md:344](../domain-model.md#L344); this PASS relies on the enclosing limits, not on an explicit review counter. |
| 4. Can a controller restart produce a duplicate worker or duplicate commit? | **FAIL** | Duplicate prevention across controller restart is not established. Same-key provider retries are specified, but recovery is not required to reconcile outstanding invocations and reuse their persisted requests before dispatching more work. Commit application has no corresponding idempotency/reconciliation protocol. See [design/worker_provider.md:85](../worker_provider.md#L85), [design/worker_provider.md:125](../worker_provider.md#L125), [design/domain-model.md:506](../domain-model.md#L506), and [design/transition-matrix.md:275](../transition-matrix.md#L275). F01-002 and F01-003. |
| 5. Can a partially-implemented stage be represented without lying about status? | **PASS** | Yes. `declared_status`, `observed_satisfaction`, and lifecycle are separate. `PARTIAL` represents some mandatory criteria met with others unevaluated; a mixture containing failures is `UNSATISFIED`, with the completed criteria still retained individually. Neither case requires claiming completion. See [design/domain-model.md:198](../domain-model.md#L198), [design/domain-model.md:229](../domain-model.md#L229), [design/domain-model.md:236](../domain-model.md#L236), and [design/domain-model.md:246](../domain-model.md#L246). |
| 6. Can a new roadmap format be added without changing controller code? | **PASS** | Yes, at the specified interface boundary. A format adapter produces the common `NormalizedRoadmap`/`StageDescriptor` types through `fetch` and `normalize`; the locator is opaque to core and lifecycle mapping depends on normalized results. See [design/roadmap_adapter.md:24](../roadmap_adapter.md#L24), [design/roadmap_adapter.md:54](../roadmap_adapter.md#L54), [design/roadmap_adapter.md:67](../roadmap_adapter.md#L67), and [design/roadmap_adapter.md:100](../roadmap_adapter.md#L100). |
| 7. Can repository drift invalidate an approval issued earlier? | **FAIL** | The design invalidates measured evidence, but does not specify invalidation of the approval itself. An unconsumed approval has subject, scope, optional expiry and displayed artifacts, without a required snapshot binding or a rule requiring renewed approval after those artifacts become stale. Fresh validation can therefore accompany an old approval. See [design/domain-model.md:591](../domain-model.md#L591), [design/domain-model.md:599](../domain-model.md#L599), [design/domain-model.md:605](../domain-model.md#L605), [design/evidence-model.md:199](../evidence-model.md#L199), and [design/transition-matrix.md:60](../transition-matrix.md#L60). F01-004. |
| 8. Is the commit path safe if the process dies between commit and receipt? | **FAIL** | Safety is not established. `APPLYING` can outlive a successful repository mutation without a persisted `CommitReceipt`. The specified atomic transaction covers the audit event and log head, not the repository operation; no recovery rule identifies and adopts an already-landed commit. See [design/transition-matrix.md:275](../transition-matrix.md#L275), [design/domain-model.md:557](../domain-model.md#L557), [design/domain-model.md:564](../domain-model.md#L564), and [design/evidence-model.md:132](../evidence-model.md#L132). F01-003. |

| F01-001 | BLOCKER | true | [design/authority-matrix.md:238](../authority-matrix.md#L238) | **Activation can turn a worker request into authority without the required grantor.** Steps 1–9 intersect the requested set with ceiling, mode and role, then check grant provenance only for HUMAN-class capabilities at line 243. `roadmap.writeback` is ORD but grantable only by `HUMAN_PRINCIPAL` (line 74). A planner can author a draft requesting it ([design/domain-model.md:311](../domain-model.md#L311)); the planner's conditional role cell retains it (authority matrix line 216), and autonomous activation needs no confirmation ([design/transition-matrix.md:213](../transition-matrix.md#L213)). With the capability in the project ceiling but no human grant, the algorithm still grants it. A nonempty chain citing ceiling and role does not repair this: those sources only bound or narrow grants (authority matrix lines 30–32). The algorithm contradicts the grantor register and default-deny rule. |
| F01-002 | MAJOR | true | [design/worker_provider.md:125](../worker_provider.md#L125) | **Worker dispatch has no controller recovery contract.** The sequence records DISPATCHED, calls the provider, then records the receipt. A controller can die while the first invocation is running or after its output is returned but before the receipt is durable. WP-6 guarantees deduplication only when the same key is resubmitted. No restart procedure requires replaying the saved request, reconciling in-flight work, or preventing a replacement invocation with rebuilt context or a new attempt/key. The key depends on context, role and attempt ([design/domain-model.md:506](../domain-model.md#L506)); one nonterminal run per stage does not prevent multiple workers within that run (domain model lines 286 and 749). The provider's same-key promise alone does not establish the requested controller-level guarantee. |
| F01-003 | BLOCKER | true | [design/transition-matrix.md:275](../transition-matrix.md#L275) | **A landed commit can remain permanently unreceipted after a crash.** The repository write occurs during APPLYING; APPLIED requires a matching receipt and post-snapshot. If the process dies after the repository commits but before that evidence is durable, the log can contain APPLYING with no receipt. There is no specified durable operation identity in the repository, recovery lookup, or reconciliation outcome for this case. The resulting revision is recorded in the receipt ([design/domain-model.md:565](../domain-model.md#L565)); the intent's trailers require only evidence back-references (line 550). The audit append transaction covers only the event and log head ([design/evidence-model.md:132](../evidence-model.md#L132)). Blind retry is not established as idempotent; the base-revision prohibition ([design/transition-matrix.md:376](../transition-matrix.md#L376)) may instead strand the successful change. Tree equality alone cannot establish which revision fulfilled which intent. Both restart deduplication and commit-to-receipt recovery remain unspecified. |
| F01-004 | BLOCKER | true | [design/domain-model.md:599](../domain-model.md#L599) | **Approvals are not bound to the repository reality the human approved.** `HumanDecision` records scope, optional expiry, nonce and `evidence_shown`, but no required snapshot/tree binding or predicate invalidating the decision when that evidence becomes stale (lines 599–614). Consider an unused STAGE approval shown snapshot S0: the workspace changes to S1, fresh validations and reviews pass, and the same stage remains the decision subject. The current-evidence rule can now pass while the old, unexpired approval still satisfies CONFIRM ([design/transition-matrix.md:60](../transition-matrix.md#L60)). Single-use prevents reuse after consumption, not stale first use. Receipt staleness ([design/evidence-model.md:194](../evidence-model.md#L194)) and the prohibition on applying a changed base revision ([design/transition-matrix.md:376](../transition-matrix.md#L376)) do not supply the missing decision-freshness rule. |
| F01-005 | MAJOR | true | [design/schema/stage_contract.schema.json:8](../schema/stage_contract.schema.json#L8) | **Legal contract status transitions cannot preserve the required contract hash.** The hash includes every member except `contract_hash`, so it includes `status` (schema lines 8 and 22). DRAFT → ACTIVE changes that preimage ([design/transition-matrix.md:213](../transition-matrix.md#L213)). Retaining the old hash fails required recomputation; replacing it violates XC-13, which permits only `status` to differ between persisted documents sharing a contract ID ([design/schema/stage_contract.schema.json:502](../schema/stage_contract.schema.json#L502)). Later ACTIVE → FULFILLED/REVOKED/EXPIRED transitions also conflict with the pinned run hash ([design/domain-model.md:266](../domain-model.md#L266)). No legal representation satisfies these rules together. |
| F01-006 | MAJOR | true | [design/transition-matrix.md:105](../transition-matrix.md#L105) | **Cross-axis guards deadlock startup and initial dispatch.** PLANNING → ACTIVE requires a READY stage (line 88), but every stage transition, including PENDING → READY, requires the project already to be ACTIVE or SETTLING (lines 105–111). Even granting the adapter's initial materialization rule ([design/roadmap_adapter.md:102](../roadmap_adapter.md#L102)), no first stage can legally become READY during PLANNING. A second cycle exists at dispatch: CONTRACTED → RUNNING requires a DISPATCHED run (transition matrix line 116), that run state requires provider acceptance of a worker (line 183), and the composition table denies worker dispatch while the stage is CONTRACTED (line 309). No stated exception breaks either cycle. These defects apply in both governance modes. |
| F01-007 | MAJOR | true | [design/evidence-model.md:75](../evidence-model.md#L75) | **Judgmental reviews are simultaneously forbidden and required as transition evidence.** Automated and peer-worker review verdicts are classified as CLAIM; direct CLAIM → EVIDENCE promotion is forbidden (line 91). G-1 further excludes Review from entities permitted as `required_evidence` ([design/domain-model.md:767](../domain-model.md#L767)). Yet the transition matrix requires `RVW` as evidence for satisfaction ([design/transition-matrix.md:127](../transition-matrix.md#L127)), and the satisfaction evaluator consumes Review records directly ([design/evidence-model.md:169](../evidence-model.md#L169)). Computing independence does not define a separate evidence record or an exception to G-1. Enforcing the taxonomy blocks judgmental completion; enforcing the transition/evaluator rules lets worker claims gate satisfaction contrary to that taxonomy. |
